## 3. 响应结构

成功失败**同构**，前端统一解析：

```json
{
  "code": 0,
  "message": "成功",
  "traceId": "a1b2c3d4e5f6",
  "data": { }
}
```

- `code=0` 是唯一成功标志，**不要用 HTTP 状态码判断业务结果**
- `traceId` 必须记录在缺陷单里，用于拉整条链路日志
- 所有 `Long` 主键与金额已序列化为 **String**，前端按字符串处理，禁止 `parseInt`

## 4. 重要：`2001` 的真实语义（与旧文档不符）

| 文档旧文案 | 代码真实行为 |
| --- | --- |
| "重复请求，已返回首次结果" ❌ | "同一请求**正在处理中**，首次结果尚未落库" ✅ |

**后端实现方式：** 幂等不是靠"记录首次结果再回放"，而是靠 **`Idempotency-Key` 派生业务单号 + 数据库唯一约束**。

```
transferNo = "T" + sha256(payerId + ":" + IdempotencyKey).substring(0, 24).toUpperCase()
```

因此实际行为是：

| 场景 | 返回 |
| --- | --- |
| 首次请求 | `code=0` + 正常结果 |
| **重复请求（已完成）** | **`code=0` + 首次结果**（不是 2001！） |
| 并发同 Key（未落库） | `2001`，稍后重试 |

**测试注意事项：**
- 断言"重复提交返回 2001" → **会失败**，应断言 `code=0` 且单号相同
- 断言"并发同 Key 只落 1 行" → 正确，查数据库行数

## 5. 两条敏感词处置口径（有意设计，测试勿当 Bug）

同一套词库，两条不同处置路径：

| 场景 | 命中后 | 为什么 |
| --- | --- | --- |
| 发动态 / 发评论（M5） | **不报错**，`audit_status=3` 转人工，`publish_status=0` 仅作者可见 | 内容社区"先审后发"，用户不该看到"发布失败" |
| 发 IM 消息 / 转账备注 / 二手挂售描述 | **直接拒绝 `4001`** | 即时通讯与资金指令不能进队列，必须当场拦 |
